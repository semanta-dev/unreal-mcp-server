# Editor Plugin Plan — the MCP Cockpit

**Status:** Fifth draft (revised after gamedev A- / eng10x A- gates converged on 13 precise fixes), for A+ re-review.
**Owner:** unreal-mcp-server.
**Scope:** A polished Unreal **Editor** plugin plus a Go-hosted human **cockpit** that together turn the existing headless RPC surface into a first-class control tower — a live view a developer keeps open all day while an AI agent drives their editor **and they keep working in it too**, seeing every action (and *why*) and live editor/world/PIE state, with honest human-in-the-loop control (pause / step / **inspect-then-approve** / intervene / stop) that never freezes the human's own hands, backed by a robust native control + observability channel that supersedes the fragile parts of today's hot-loaded Python bridge.

> **The one-line thesis.** Today control and observation are two half-blind, out-of-band paths bolted onto Epic's Python remote-execution channel: a single-flight, marker-scraping, reverse-connect command socket for *doing*, and filesystem polling for *seeing*. We keep the enormous semantic investment (the `mcp_bridge.py` op table and the 120 MCP tools) but move it onto a **plugin-hosted, forward-connect, framed, pushed** channel, and we put a **human cockpit** in front of the dispatch path. That cockpit is a **two-surface system**: an **always-live, out-of-process primary view hosted by the Go server** (never blocked by the editor game thread) — a fully-specified, authenticated, first-class deliverable — plus a **thin in-editor Slate status strip** for launch/STOP convenience. So a developer can *watch, inspect, gate, and stop* an agent — including during the exact ops that freeze the editor — the agent finally gets a real event stream, and **the human keeps a responsive editor while the agent works beside them.**

> **What this draft fixes (deltas from the fourth draft — the 13 converged fixes).** The fourth draft earned A-/A- from a shipped-titles game dev and a 10x engineer, both of whom called it "A+ as an architecture+safety document" and then handed over one precise punch-list. This draft applies every item:
> 1. **The approval gate is a real inspection surface, not a rubber-stamp** (§4.2): because the plugin owns game-thread dispatch, at park time it **reads the target's current value(s)** for mutating ops and puts a **before→after diff** in the gate frame; each gate row has a **"Select/Focus target in editor"** action that temporarily selects+pilots to the target under the save/restore contract then restores; and the in-editor `FSlateNotificationManager` toast is **actionable** (inline Approve/Deny, coalesced under a burst) — actionable in-editor approve is pulled into **Phase C**. *(gamedev blocker.)*
> 2. **Co-working ergonomics — the agent never freezes the human's editor** (§4.4): the dispatch core has **human-input-aware throttling** — when a human is actively interacting (recent input / focused viewport or details panel, via `FSlateApplication::GetLastUserInteractionTime`), the core inserts a **yield/rate-limit between agent ops** (a `UMCPSettings` governor: max agent ops/sec while human active), so the human gets game-thread cycles. This delivers the flagship "dev works while agent works" promise instead of merely being honest about the freeze. *(gamedev blocker.)*
> 3. **The HITL gate is bound to the tool call's lifetime** (§4.2): on MCP client-disconnect / context-cancel during park, the pending gate is **cancelled** and is **not** executed on a later Approve (a human who approves an abandoned gate sees **`AGENT_SEVERED`**); `GateTimeout` is **capped to a documented safe fraction of the MCP/HTTP request timeout** so a parked gate can never outlive its call. *(eng10x blocker.)*
> 4. **Source-control + save side effects are first-class** (§5.2/§5.3/§3.4): SCC-mutating ops (save-with-checkout, add, revert) are classified **mutating+gateable**; a cockpit **"N packages modified (M dirty / K saved / J checked-out)"** panel is driven by package-dirty + `ISourceControlProvider` state; a `UMCPSettings` policy governs whether the agent may **auto-save / auto-checkout** at all. (Repo SCC is Git-based, `internal/tools/git_tools.go`.) *(gamedev major.)*
> 5. **Spatial legibility of level edits** (§3.5/§5.2): an **editor-viewport thumbnail** is auto-captured per mutating op (or per `task_id`) **framed on the op's target bounds** (`AActor::GetActorBounds` + editor-world SceneCapture), linked into the filmstrip/feed-row; it is rate-limited + cost-budgeted; an optional **"follow the agent"** toggle pilots the human viewport to the agent's current target. *(gamedev major.)*
> 6. **Undo/redo honesty — the redo-stack clobber** (§4.3): every agent `BeginTransaction` on the shared `GEditor->Trans` **clears the human's redo stack**; we name it and mitigate — **defer opening the next agent batch while the human has a non-empty redo stack** (else warn in the cockpit). *(gamedev major.)*
> 7. **Asset-level concurrency** (§4.4): the actor-centric `CONFLICT` model is extended to **asset scope** — a mutating/compile op targeting an asset open in an editor (`UAssetEditorSubsystem::FindEditorsForAsset`) is gated **`ASSET_OPEN_IN_EDITOR`** or soft-locked under the §4.4 toggle, so the agent can't silently recompile a Blueprint the human has open. *(gamedev major.)*
> 8. **Cockpit push+auth committed to one mechanism** (§3.2): we **drop `EventSource` for `fetch()` + `ReadableStream`**, which carries `Authorization: Bearer` natively and lets us drive `Last-Event-ID`→`replay-from(seq)` resume ourselves — resolving the fourth draft's own open blocker (no polyfill/token-in-URL waffle). *(eng10x major.)*
> 9. **RPC concurrency & queueing is stated explicitly** (§5.6): Tier-P is **strictly serialized on the game thread (exactly 1 executing)**; rpcs **queue with bounded depth D** and are rejected with a distinct **`QUEUE_FULL`/`BUSY`** beyond D; **head-of-line blocking is acknowledged** and is the concrete reason long work MUST run Go-side-async. *(eng10x major.)*
> 10. **Native-path completion is reconciled per op** (§5.1): because `ExecPythonCommandEx` is **synchronous**, after it returns the dispatch core checks whether `emit_result(op_id)` fired; if not, it **synthesizes an `EDITOR_EXEC_FAILED` envelope** (carrying `bCommandSuccess` + any `FPythonLogOutputEntry` errors) so an rpc **always** terminates — no silent hang. *(eng10x major.)*
> 11. **Capture/journal cost is bounded and soak-tested** (§6.2/§7/§8): capture **rate-limit + on-disk frame-retention cap + per-frame cost budget** live in `UMCPSettings`; an **8-hour SOAK gate** is added to Phase D (sustained op stream; memory/handle stability across ring, journal rotation, SSE reconnect churn, virtualized feed; no unbounded growth). *(gamedev minor.)*
> 12. **PIE injected-input observability** (§3.4/§6.1): the PIE/State pane surfaces **live held keys/axes** (from `MCPControlSubsystem::HeldKeys`) and a clear **"input released"** confirmation when `ReleaseAll` fires. *(gamedev minor.)*
> 13. **Phase A is split into A0 and A1** (§8.1): **A0** = `MCPCore` transport + event bus + ring + `cockpit_info`/epoch/token, provable **headless** against the protocol-extended `fakeeditor`, **zero Slate**; **A1** = the Go-hosted cockpit SPA + auth + SSE + the **<100 ms STOP-ack** gate + the Slate strip. *(eng10x minor.)*
>
> **Retained, verified corrections from the fourth draft (unchanged and still load-bearing):** primary surface out-of-process because Slate ticks on the game thread that freezes during every Tier-P op (§1.1, §2.6); fail-closed conformance-tested classification table as the security boundary (§5.3); the arbitrary-exec hole named and contained with an `AllowRawExec` hard mode (§5.5); coalesced/time-boxed/size-boxed labeled agent-undo batch, no double-wrap of self-transacted ops, cockpit-owned agent-undo (§4.3); Go-side gate park bound to an `args_hash` so the model never sees `PENDING_APPROVAL` (§4.2); plugin-minted `session_epoch` (not uexec `Generation()`) as the sole reset authority, with the Live-Coding self-decapitation branch (§2.5, §2.7); ephemeral `127.0.0.1:0` bind (§2.4); native result callback, not marker scraping (§5.1); per-thread staging for wait-free `FOutputDevice::Serialize` and the scoped/capped/storm-suppressed property firehose (§6.2); headless-safe `Editor` transport module, Slate only in `EditorNoCommandlet` (§2.7); selection stewardship save/restore contract (§4.4); intent-first feed rows (§3.4).

## 1. Vision & non-goals

### 1.1 Who the user is, and where they watch

A **game developer sitting in front of their own editor while an AI agent works inside it — and who keeps working in that editor at the same time.** They have the Unreal Editor open, a level loaded, maybe a PIE session running. An agent (Claude, via `unreal-mcp.exe`) is spawning actors, editing blueprints, launching PIE, taking screenshots, running builds. Today that developer is **flying blind**: the agent's actions land in their editor with no trace of *who did what, when, why, and whether it worked*, the agent hitches their editor whenever it likes, and the only human-facing safety is an RPC (`ReleaseAll`) they cannot press.

**Where the developer watches matters, and it is the crux the second draft got wrong.** During a Tier-P op the editor game thread is blocked (§2.6), and Slate ticks on that thread — so an *in-editor* live view goes dark precisely during the ops the human most needs to watch and stop. Therefore the cockpit's **primary, always-live surface is out-of-process, hosted by the Go server** (§3.2), which owns the full seq'd event stream and is never blocked by the editor. The in-editor Slate presence is a thin status strip (STOP + connection + launch), live *between* ops (§3.3).

**Co-working is a first-class promise, not a caveat (fix #2).** "The developer keeps working while the agent works" is only true if the agent does not monopolize the game thread. The dispatch core therefore **yields to the human**: when it detects recent human input or a focused viewport/details panel, it rate-limits agent ops so the human's own drags, selections, and edits get game-thread cycles between agent ops (§4.4). We deliver co-working; we do not merely disclose the freeze.

Through the primary (Go-hosted) cockpit the developer can, continuously and even while the editor is frozen mid-op:

- **SEE** every agent action as it happens — the agent's **intent/rationale** as the headline, with tool name, exact args, result or error, and elapsed time expandable beneath — as a live feed (§3.4).
- **SEE** the live editor/world/selection/PIE state, the **held injected-input** set (§3.4/§6.1), the **packages the agent has touched** (§3.4/§5.2), and the structured log/issue stream, *synchronized* with that feed by a single `seq` space.
- **SEE what the agent sees** — a mirror of the exact event/rpc frames the agent received **and a live filmstrip of the actual frames the agent captured**, including an **auto-captured editor thumbnail framed on each mutating op's target** (§3.5).
- **INSPECT before approving** — each pending gate shows a **before→after diff** of the exact change and a one-click **"Select/Focus target in editor"** so the human eyeballs the real object before deciding (§4.2).
- **INTERVENE** — pause the agent between ops, step it, approve/deny risky actions before they execute, take over by hand, and hit a stop-switch whose **in-browser ack lands in < 100 ms** — all within the honest limits of what the game thread allows (§2.6, §4.5).
- **TRUST** the tool: a shippable, cooked-strippable plugin plus a **secured, authenticated** local cockpit that does not tank their editor's frame rate — and a human view that stays alive when the editor does not.

### 1.2 What "control + observability from inside the editor" means

| Dimension | Today (ground truth) | Cockpit target |
|---|---|---|
| Human UI | **None.** No `SDockTab`, no `UToolMenus`; `StartupModule`/`ShutdownModule` are empty (`MCPCaptureModule.cpp`, `MCPAuthoringModule.cpp` are bare `IMPLEMENT_MODULE`). | **Primary:** Go-hosted out-of-process cockpit (authenticated local web UI + TUI), always live. **Secondary:** thin in-editor Slate status strip. |
| Observation | Poll-based: `editor_events` tails `Saved/PyMCP/events.ndjson` by byte offset (`internal/events`); capture manifest; crash dumps. **No push.** | Single ordered, **pushed**, sequence-numbered event stream (PIE, map, save, selection, property, transaction, log, op lifecycle, **held-input**, **package/SCC**) + captured-frame + per-op editor-thumbnail filmstrip. |
| Control channel | Epic Python remote-exec: single-flight reverse-connect TCP, ~120 s timeout, `__MCP_JSON__` marker-scraped stdout, tainted-connection churn (`internal/uexec/command.go`). | Plugin-hosted **forward-connect framed** channel on an **ephemeral loopback port**; out-of-band control that severs the channel off-thread and enqueues game-thread actions (STOP), honored at the next yield. |

### 1.3 Non-goals (explicit, to keep this shippable)

- **Not** a from-scratch reimplementation of the Python ops in C++. Reflection ops (`pie_observe`, asset walks) stay Python; that is the right tool. We move the *transport and the control surface*, not the op semantics.
- **Not** a remote/networked control surface. Loopback only, project-scoped, same trust boundary as today. The Go-hosted cockpit UI is a **local, token-authenticated** web/TUI on loopback; no cloud, no external auth server — but it is **not** an *unauthenticated* local surface either (§3.2 closes the local-process/CSRF hole).
- **Not** a replacement for the agent's own UI. The cockpit is the *human's* window into the agent's activity, not a chat client.
- **Not** shipped into cooked/shipping games. The cockpit's plugin side (transport + native editor control) lives in `Editor`/`EditorNoCommandlet` modules and is stripped from builds; the `Runtime` capture/input module stays, exactly as today.
- **Not** a promise the plugin can preempt Python. We are explicit (§2.6) that a monolithic Tier-P op cannot be interrupted mid-flight and will hitch the game thread for its full duration; the design — the out-of-process primary surface, the honest deferred-STOP model, **and yield-to-human pacing that bounds how often we take the thread** — is built *around* that constraint, not in denial of it.

## 2. Architecture — the big decision

### 2.1 The decision: **Augment, then absorb the transport — keep the op bodies, change only the emit sink.**

Three options. I reject two and commit to a phased hybrid.

- **(A) Replace** the Python bridge wholesale with native C++ dispatch. **Rejected.** `mcp_bridge.py` is 2824 lines feeding 120 MCP tools across 36 tool files. Nearly all of it is *reflection* over the `unreal` module. Rewriting that in C++ is a multi-month regression factory with no user-visible benefit — the reflection is *why* it stays current across engine versions with zero code.
- **(B) Augment only** — add a cockpit UI that *reads* state, leave the transport. **Rejected as the end state.** It leaves every enumerated fragility intact: single-flight blocking, marker scraping, reverse-connect flakiness, tainted-connection churn, no push. A cockpit that can only *watch* a blocked channel cannot deliver an approval gate or a real stop-switch.
- **(C) Phased hybrid — augment first, then move the transport under the existing op bodies.** **Chosen.** The key realization: the plugin runs *inside* the editor process, so it can execute the existing Python op bodies **in-process** via `IPythonScriptPlugin::Get().ExecPythonCommandEx(...)` — with **no reverse-connect socket, no stdout round-trip, and (via a native result callback, §5.1) no marker scraping.** We reuse every op *body* unchanged; the **only** change to `mcp_bridge.py` is the emit sink (`_emit`/`_emit_event` — verified the sole sinks at `mcp_bridge.py:63`/`:2479` — route to a native callback when it is present, else fall back to printing the marker for the uexec path). We get the cockpit's control authority *because the plugin now owns the dispatch path*.

**Precise claim (correcting the first draft):** we do **not** "reuse the `_OPS` table verbatim." We reuse the op *function bodies* verbatim; a ~15-line shim in the two emit helpers is the price of dropping the marker. That surgical change is what makes "no marker scraping" true rather than aspirational. See §5.1 for the exact mechanism and which functions change.

**Why this is the correct call for *this* codebase:** the fragilities in the ground truth are all **transport/observability** fragilities (marker scraping, single-flight, reverse-connect, tainted churn, poll-only, split-brain ordering) — not *semantic* ones. Fix the layer that is actually broken; preserve the layer (op reflection) that is actually good.

### 2.3 How the parties relate

- **The plugin** is the source of truth and the authority. It owns the editor state, hosts the listener (on an ephemeral loopback port), owns op dispatch **and the bounded rpc queue (§5.6)**, mints the `session_epoch` and per-session token, **owns the classification table (the security boundary, §5.3)**, reads targets to build **gate diffs (§4.2)**, tracks **package/SCC state (§5.2)**, and enforces the human's policy — including **yield-to-human pacing (§4.4)**. It is the *only* party that can touch `GEditor`/Slate/UObjects, and it does so **only on the game thread**. It also hosts the *secondary*, thin in-editor Slate status strip.
- **The Go server** is a smart proxy **and the host of the primary human cockpit.** It selects **exactly one** transport backend per session (native cockpit channel when the plugin handshakes; Python reverse-connect otherwise, §5.4), merges the native capability manifest with the Python op table into one tool surface, fans the pushed event stream into the existing observation tools, remains the daemon's multi-project router (`internal/daemonwire`), and — critically — **serves the always-live, authenticated human cockpit and owns the approval-gate park loop bound to each tool call's context** (§3.2, §4.2). Because it is a separate process, it is never blocked by the editor game thread, so it acks STOP instantly and keeps the feed painting while the editor is frozen mid-op.
- **The agent is unchanged in contract**, and this draft makes that literally true. Same MCP tools, same `OpError` codes. A gated op does **not** surface a new `PENDING_APPROVAL` error to the model — `internal/cockpit` parks the tool call and transparently re-dispatches on approve (§4.2), so the agent sees only a slower call. It gains a *real* event subscription (push, not poll), honest progress/gate/cancel semantics, and one new **optional** field it may populate — a per-call `intent` string that becomes the feed headline (§3.4). It may observe new terminal codes (`QUEUE_FULL`, `EDITOR_EXEC_FAILED`, `CONFLICT`, `ASSET_OPEN_IN_EDITOR`, `AGENT_SEVERED`) but never a wedged hang. It does not know or care which backend ran an op.

### 2.4 Transport choice: `FTcpListener` framed JSON, forward-connect

A **single persistent bidirectional TCP socket** hosted by the plugin (`FTcpListener`, `Networking` module; `OnConnectionAccepted` fires on its own thread — `TcpListener.h:39/:129`), carrying **length-prefixed framed JSON**, over the alternatives:

- **vs. keep Python reverse-connect** — reverse-connect is a documented flake source (the editor must call back within `6×5 s` or the whole thing fails; see `internal/uexec/command.go` `open()`). Forward-connect (Go dials the editor) is strictly simpler and lets the editor advertise readiness. Framing plus the native result callback (§5.1) removes marker scraping outright.
- **vs. `FHttpServerModule` REST** (`HttpServerModule.h:55`) — request/response HTTP is awkward for **server push**, the whole point of the observability plane. I still expose a *read-only* HTTP route (`/healthz`, `/manifest`) on the editor side for trivial probing, but the primary editor↔Go channel is the framed socket. (Note: the *human-facing* cockpit HTTP server is a **separate** Go-side server, §3.2 — not this editor-side route.)
- **vs. `TcpMessaging`/`UdpMessaging`** — heavier pub/sub machinery than a single loopback socket needs; more surface to version.

**Bind address is ephemeral (`127.0.0.1:0`).** The listener requests an OS-assigned port so two concurrent editors — the headline multi-project scenario — never collide. This mirrors the daemon's existing precedent for the reverse-connect channel (`spawner.go:74` sets `CommandAddr = "127.0.0.1:0"`). The assigned port is the **sole source of truth**, discovered via `cockpit_info` (§2.5); `UMCPSettings` exposes only a `0 = ephemeral` hint (or an optional scan range), never a hard fixed port.

**Frame types (one ordered stream, one seq space):**

| Frame | Dir | Purpose |
|---|---|---|
| `hello` / `welcome` | ↔ | Handshake: protocol version, engine version, project, **plugin-minted `session_epoch`**, capability-manifest digest, echoed token, `last_seen_seq` (§2.5). |
| `rpc` / `rpc_result` | Go→UE / UE→Go | Op invocation + framed result (`{ok,result,error,code,retryable,traceback}` — same envelope as today, no marker). The `rpc` frame carries an optional **`intent`** string (agent rationale) and an optional **`task_id`** for grouping (§3.4). Beyond queue depth D the plugin returns `QUEUE_FULL` (§5.6). |
| `progress` | UE→Go | Long-op progress (build %, capture frame N) — impossible today. |
| `event` | UE→Go | Pushed observation (`{seq,t_wall,t_engine,type,payload}`). |
| `control` | Go→UE / UE→Go | Out-of-band: cancel(op-id), pause/step/resume, stop, set-policy, approve/deny(gate_id), **focus-target(gate_id)**, replay-from(seq). |
| `gate` | UE→Go | An op is parked pending human approval; carries `gate_id`, op-id, classification, **the `args_hash` the human is approving, and a before→after `diff` of the target's current value(s)** (§4.2). |

**What "out-of-band" actually buys us (honest).** Control frames are drained by the socket **rx thread**, so a `stop`/`cancel`/`pause` frame is *received* and *parsed* off the game thread even while a Tier-P op is mid-flight. But acting on it splits into two categories (the crux the first draft glossed):

- **Off-thread-immediate:** set the cancel/latch flag, refuse to *start* the next rpc, reject queued rpcs with `CANCELLED`, and sever the control plane. These happen the instant the frame arrives (**budget: < 50 ms**, §4.5).
- **Game-thread-deferred:** anything touching `GEditor`/input/PIE (`ReleaseAll`, `RequestEndPlayMap`, undo) must run on the game thread and therefore **waits for the current Tier-P op to finish and yield.** It cannot preempt a running Python call. Worst-case latency = the in-flight op's remaining game-thread time (the honest, unbounded number, §4.5).

The **STOP ack** the human sees is *neither* of these — it is produced by the Go server the instant the human clicks, independent of the editor (**budget: < 100 ms in-browser**, §4.5). §2.6 states the resulting guarantee precisely.

### 2.5 Discovery, epochs, token, and the reconnect state machine

**The pong is Epic's, not ours.** Verified: the UDP `pong` is emitted by Epic's `remote_execution.py` (`_TYPE_PONG`, `_RemoteExecutionNode`); Go parses it opaquely (`internal/uexec/node.go` `pongMeta`). Neither the plugin nor `mcp_bridge.py` can append to it without patching engine Python. The first draft's "advertise `cockpit_port` in the pong" / "mint the token in the pong" are therefore **impossible** and are removed. We bootstrap over the channel we already own.

**`cockpit_info` is a native-presence probe (stated explicitly).** The `cockpit_port`, `session_epoch`, and `token` all originate in `MCPCore` (C++). The Phase-A `cockpit_info` op is a **Python one-liner that reads them from the native `MCPCockpitBridge` object** (a module global the plugin sets when `MCPCore` is loaded). Therefore:

- If `MCPCore` is compiled and loaded, `cockpit_info` returns `{cockpit_port, session_epoch, token, protocol_version}`.
- If the native module is **absent or not loaded**, the one-liner returns an explicit **`{cockpit: "not_present"}` sentinel** (no exception, no guessing). The backend selector (§5.4) treats the sentinel as the — already one-way — trigger to stay on the uexec/Python fallback. A bare non-editor commandlet (no `GEditor`, no `MCPCore`) always hits this path.

**`session_epoch` is plugin-minted and authoritative — *not* uexec `Generation()`.** This is the second draft's error, corrected. `Generation()` (verified `internal/uexec/client.go:120-127`, comment: *"increments each time a new command channel is opened (initial connect, reconnect, or editor restart)"*) bumps on **every** channel open, including a transient reconnect after an ordinary op-timeout taint where the editor did **not** restart and in-editor state did **not** reset. Keying replay on it would fire spurious full replays on routine timeouts. So:

- `MCPCore` mints a fresh `session_epoch` (a random 64-bit / FGuid) **once per transport-singleton boot** — i.e., on editor start (and *only* on a genuine `MCPCore` reload, which §2.7 makes non-routine by excluding it from Live Coding), exactly when in-editor transport/dispatch state resets. It is stable across socket reconnects **and across Live Coding compiles of other modules.**
- `session_epoch` (returned in `cockpit_info` and echoed in `welcome`) is the **sole authority** for "did editor state reset → replay/re-sync."
- uexec `Generation()` is demoted to a mere **"connection changed — re-run `cockpit_info` to re-validate epoch+token+port"** trigger. It never *is* the epoch.

**The bootstrap + reconnect as an ordered state machine** (who drives each step):

1. **Go — lease.** Discover and lease the editor exactly as today (`pickNode`/`nodeMatchesProject`/`StrictNode`) over Epic's pong — unchanged. Establishes that an editor exists.
2. **Go — probe.** Call `cockpit_info` over the existing uexec/Python channel.
   - `not_present` sentinel → native module absent → **one-way fallback to uexec** for the session (§5.4). Stop.
   - Otherwise capture `{cockpit_port, session_epoch, token, protocol_version}`.
3. **Go — epoch compare.** Against the last-known epoch for this project:
   - **Unchanged** → editor state did *not* reset; a prior in-flight rpc (single-flight ⇒ at most one) may still be valid; request `replay-from(last_seen_seq)` only to fill the gap.
   - **Changed / first attach** → editor restarted or `MCPCore` reloaded → in-editor state reset; fail any in-flight rpc with a distinct `EDITOR_RESET` code (its outcome is unknown — never silently retried); plan a full re-sync.
4. **Go — dial.** Forward-dial `127.0.0.1:cockpit_port`; send `hello{token, last_seen_seq, known_epoch}`.
5. **Plugin — admit.** Verify token + project (loopback-only, parity with `StrictNode`); reply `welcome{session_epoch, manifest_digest, protocol_version}`. Reject mismatched token/project/peer.
6. **Go — manifest.** If `manifest_digest` differs from cache, re-fetch the manifest and re-merge the tool surface (§5.3).
7. **Plugin — replay.** Serve `replay-from(last_seen_seq)`: from the in-memory ring, then from `journal.ndjson` beyond the ring's floor (§4.6, §6.2).
8. **Go — resolve in-flight.** Any rpc mid-flight at disconnect is resolved by (a) its `rpc_result` arriving in replay (op completed editor-side) or (b) `EDITOR_RESET` if the epoch changed. The agent's tool call sees a normal (possibly slower) result or a definite error — never a silent hang.

**The self-decapitation branch (gamedev major, retained).** A special case of step 8: the in-flight op *is what severed the channel.* The two triggers are (a) the agent's own `live_coding_compile` (verified `_op_live_coding_compile`, `mcp_bridge.py:256`) or a human Ctrl+Alt+F11 that reloads a module, and (b) any op that reloads/reinstances `MCPCore` itself.

- **§2.7 makes case (a) safe:** `MCPCore`'s transport singleton is *excluded from Live Coding reload*, so a compile of game/project modules leaves the socket, ring, and `session_epoch` intact — the channel does **not** sever, the epoch does **not** bump, and the compile's `rpc_result` returns normally (streamed as progress per §2.6 rule 1, not a blocking call the reload could orphan).
- **For case (b)** — a genuine reload of `MCPCore` (only possible via a full rebuild/editor restart now, never routine hot-reload): the socket drops, a fresh singleton boot mints a **new `session_epoch`**, and on reconnect Go's epoch-compare (step 3) sees the bump and resolves the in-flight op as `EDITOR_RESET` — a definite outcome, not a silent hang — then transparently re-establishes the session. The agent's tool call returns `EDITOR_RESET` (unknown outcome, never auto-retried); the human sees a clean "editor transport reloaded — session re-attached at epoch N" banner rather than a wedged feed.

*(Alternative considered and rejected: a plugin-emitted multicast beacon on a distinct message type. It works but adds a second discovery mechanism and more surface to version; the bootstrap-op path is cleaner and already gated by the existing lease.)*

### 2.6 Honest limits: game-thread preemption (the load-bearing constraint)

This subsection is the plan's spine. Everything downstream (STOP, the ≤2 ms budget, the phase gates, the pacing governor) is scoped to it.

- **Tier-P ops are non-preemptible.** `IPythonScriptPlugin::ExecPythonCommandEx` runs **synchronously on the game thread** (the Python GIL/interpreter is bound there, and the op bodies assert on `GEditor`/UObjects). A single Tier-P op — an asset walk, `pie_observe`, `execute_console_command`, a blueprint compile — is **one indivisible work unit.** There are no "between work units" flag checks inside it. It runs to completion. Exactly one executes at a time (§5.6).
- **While a Tier-P op runs, the game thread is blocked — and so is the in-editor Slate strip.** Slate ticks on the game thread, so the *secondary* in-editor strip is unresponsive for the op's full duration. **This is exactly why the primary surface is out-of-process** (§3.2): the Go-hosted cockpit keeps painting the feed, flips the BUSY banner, and acks STOP while the editor is frozen. We do not hide the freeze; the Go side *renders* it (from the `editor.busy` event and its own heartbeat-gap detection, §3.6).
- **What we therefore promise:** out-of-band control lets the Go server **ack STOP in-browser in < 100 ms** and **enqueue** a stop/cancel that fires the *instant the current op yields the game thread*, plus off-thread severing that is immediate (reject next/queued rpcs, cancel Go-side jobs, close the control plane — **< 50 ms**). We **do not** promise mid-op interruption of a monolithic Tier-P op; the worst-case *game-thread* effect latency equals the in-flight op's remaining time (unbounded in principle — see §4.5's honest model and published p50/p99).
- **How we make the promise strong anyway — five mitigations, all in-plan:**
  1. **Keep genuinely-long work off the game thread.** Builds, cooks, and long captures already run as **Go-side async subprocesses** (`internal/build/run.go`, capture recorder) — never placed behind a blocking `ExecPythonCommandEx`. New long work follows the same rule: it returns a job handle and streams `progress`, so STOP can cancel the *subprocess* off-thread. **This rule now also covers `live_coding_compile`/build triggers** — they stream progress via the Go-side async path rather than block the framed channel that a module reload would kill (§2.5 self-decapitation). **Head-of-line blocking on the single serialized game-thread slot (§5.6) is the concrete reason this rule is mandatory, not a preference.**
  2. **Per-op game-thread time budget + watchdog.** The dispatch core stamps each op's start; a watchdog on the rx/timer thread emits an `editor.busy{op, elapsed_ms}` event once an op exceeds a threshold (default 250 ms). The Go cockpit flips a live "EDITOR BUSY — op X for N s (queued STOP pending)" banner. The human sees *why* the editor is frozen — on a surface that is *not* frozen.
  3. **Decompose resumable ops into ticked units where it matters.** The capture recorder already ticks; native long ops (batch spawns, multi-asset import) are implemented as **chunked Tier-N** ops that poll the cancel flag between chunks on `FTSTicker` (≤2 ms/tick). *These* are genuinely mid-flight-cancellable — and only these.
  4. **Yield to the human between ops (§4.4).** The pacing governor bounds how *often* the agent takes the game thread while the human is actively interacting, so even a stream of short Tier-P ops cannot starve the human's own drags/selections. This does not shorten any single op; it guarantees game-thread cycles *between* ops.
  5. **STOP escalation is categorized** (§4.5) so the human knows which effects are instant (Go-side ack + off-thread severing) and which wait for the game thread to free.
- **Consequence for the ≤2 ms/tick budget:** that cap governs the **event drain** and **chunked Tier-N** work — *not* a monolithic Tier-P op, which is a single item that can and will exceed it. The budget bounds our *own* overhead, not the op bodies.

### 2.7 Module layout — transport is headless-safe, Live-Coding-durable, and Slate-independent

The first draft put the transport in `EditorNoCommandlet`, coupling the robust channel to an interactive, rendered editor — which strands the very backgrounded/headless editor that motivates the project. Corrected by **splitting the module** *and* decoupling the transport's lifetime from module reinstancing:

| Module | Type | Loads under… | Role | Change |
|---|---|---|---|---|
| `MCPCapture` | **Runtime** | game/PIE/standalone | Input injection + game-world SceneCapture (`MCPControlSubsystem`, `MCPCaptureSubsystem`, HUD/button). | Unchanged. |
| `MCPAuthoring` | **Editor** | editor + commandlet | WidgetBlueprint authoring/compile/introspection. | Retained; folded into `MCPCore`'s manifest as native ops in Phase C. |
| **`MCPCore`** | **Editor** | editor + commandlet + `-nullrhi` editor | **NEW. No Slate dependency.** `FTcpListener` server (binds `127.0.0.1:0`), dispatch core + **bounded rpc queue (§5.6)**, event bus, capability manifest + **classification table (security boundary)**, journal, `UMCPSettings`, the `UMCPCockpitBridge` result/event callbacks (§5.1), `session_epoch` + token, **package/SCC tracker (§5.2)**, native editor ops. | New module. `StartupModule` mints the epoch and boots the listener (guarded on `GEditor != nullptr`); `ShutdownModule` tears it down. **Listener/ring/epoch live in a process-lifetime singleton excluded from Live Coding reload (see below).** |
| **`MCPCockpit`** | **EditorNoCommandlet** | interactive editor only | **NEW. Slate only, SECONDARY surface — a thin status strip in Phase A** (§3.3): toolbar STOP routed through Go, connection pip, "Open cockpit" button, **actionable approval toasts in Phase C** (§4.2). **Why `Editor` (not `EditorNoCommandlet`) for `MCPCore`:** `EHostType::Editor` loads in an editor process **and** under a commandlet; `EditorNoCommandlet` loads in an editor but **not** under a commandlet (`ModuleDescriptor.h`). Putting the transport in an `Editor` module means it is available in every host that has `GEditor`.

**Live-Coding durability (gamedev major, retained).** Devs hit Ctrl+Alt+F11 constantly, and the agent has a `live_coding_compile` op. Live Coding reinstances `UObject`s and can reload a module, which would decapitate a socket/ring owned by a reinstanced object. Two-part fix:

1. **The transport is a process-lifetime C++ singleton, not a `UObject`.** The `FTcpListener`, the event ring, the dispatch queue, and the `session_epoch` live in a plain non-`UObject` singleton with process lifetime. `UMCPCockpitBridge` (the `UCLASS` the `unreal` module calls) is a thin, reinstanceable *forwarder* into that singleton — so even if the bridge object is reinstanced, the socket/ring/epoch underneath survive.
2. **`MCPCore` is excluded from Live Coding reload** (marked non-hot-reloadable / its patch is disabled for Live Coding). A routine compile of *game/project* modules therefore leaves `MCPCore`'s transport untouched — the channel stays up, the epoch does not bump, and the in-flight compile's result returns normally. Only a deliberate full rebuild/editor restart cycles `MCPCore`, which is a genuine reset (new epoch → `EDITOR_RESET` → transparent re-attach, §2.5). This is consistent with `lifecycle.go`'s own note that a stale editor can hold "the Live Coding lock" — we keep our transport out of that blast radius.

**The exact headless host we target (stated, and provable):** the project's "backgrounded/headless editor" is **`UnrealEditor.exe <project> -nullrhi`** — a real editor process (so `GEditor`, the game thread, Python, and all `FEditorDelegates` exist) with **no RHI/rendering and no initialized Slate.** `MCPCore` loads there and serves the transport; `MCPCockpit`'s strip is skipped because `FSlateApplication::IsInitialized()` is false. In that host the **only** cockpit is the Go-hosted primary surface — which is exactly why it must be out-of-process. Phase A0's exit gate proves `MCPCore` serves `rpc`/`event`/`cockpit_info` in a `-nullrhi` editor with **zero** Slate symbols touched.

Go gains `internal/cockpit` (framed client + event stream + replay + gate park + **the human cockpit HTTP/SSE server + SPA host**, §3.2) and an exclusive `bridge` backend selector; `internal/uexec` is retained as the fallback path and the rollback story. **Naming note:** `internal/cockpit` is net-new and unrelated to `internal/framing`, which is pure **camera-pose math** (not protocol framing) — no reuse, no collision.

## 3. The Cockpit — two surfaces, honestly placed

### 3.1 The decision: primary surface out-of-process (Go-hosted), secondary a thin in-editor strip

**Decision + rationale.** The single most important observability property is that the human's live view and STOP ack **stay alive during the ops that freeze the editor.** An in-editor Slate panel physically cannot — it ticks on the blocked game thread. The Go server already receives the complete seq'd event stream on a socket the editor's freeze does not touch, so it is the correct host for the always-live surface. Therefore:

- **Primary surface — Go-hosted, always live, and fully specified in §3.2.** `internal/cockpit` runs a **local, token-authenticated web UI** (its own `http.Server` on a second loopback port, pushed via `fetch()`+`ReadableStream` SSE) and a **TUI** attachable to the daemon. It renders the feed, state, logs, issues, the **captured-frame + per-op editor-thumbnail filmstrip** (§3.5), the **packages/SCC panel** (§5.2), the **held-input** set (§3.4), the BUSY banner, and the control bar; it **acks STOP in-browser in < 100 ms** (§4.5), independent of the editor. In the multi-project daemon it hosts one cockpit fronting N editors, one pane per editor (§3.2). This is the surface the README tells the developer to keep open.
- **Secondary surface — in-editor Slate status strip, thin and best-effort.** A convenience for developers who want a STOP button and a connection pip docked next to their viewport, plus a one-click "Open cockpit" launcher, plus (Phase C) actionable approval toasts so a decision never requires leaving the editor (§4.2). It is explicitly documented as going dark during a Tier-P op (§2.6) and is **never** the sole place STOP/BUSY/feed live. Any richer in-editor mirror (feed/log/filmstrip) is deferred to Phase D and gated on real demand (§3.3).

This is a deliberate reframing of the second draft, whose flagship was the Slate panel. The plugin remains the subject of this plan — it owns the channel, dispatch, event bus, native ops, settings, classification table, gate diffs, package tracker, and the secondary strip — but the *primary human live view* is correctly located out-of-process, and (this draft) fully specced and secured.

### 3.2 The primary surface — the Go-hosted cockpit, specified and secured (retained blocker; push+auth now decided)

This is the surface the developer stares at all day, so it is a **first-class deliverable**, not an afterthought. There is no existing web/TUI/HTTP-push code in the Go tree (verified: no `internal/cockpit`, no SSE/ws); it is net-new. The daemon already runs an `http.Server` for the MCP transport (`daemon.go:76`), so a second server is well-trodden ground, not a new capability.

**Server & app.** `internal/cockpit` starts an `http.Server` bound to **`127.0.0.1:0` (a second ephemeral loopback port, distinct from the editor's framed socket and from the daemon's MCP port)**. It serves a **single self-contained SPA** (HTML/JS/CSS embedded via `//go:embed`, no external assets — offline, no CDN). The chosen cockpit UI port is advertised via `cockpit_status`/the CLI banner; the CLI prints the launch URL and can open the browser.

**Push transport — decision: Server-Sent Events over `fetch()` + `ReadableStream`, not `EventSource`, not WebSocket (fix #8).** The fourth draft chose SSE but left *how* the browser authenticates the stream open ("`EventSource` polyfill or a token-scoped URL") — its own acknowledged blocker. Closed decisively: the SPA opens the event stream with **`fetch("/events", {headers:{Authorization:"Bearer <token>"}})` and reads `response.body` as a `ReadableStream`**, parsing the `text/event-stream` framing in JS. This is chosen over the two alternatives for concrete reasons:

- **vs. native `EventSource`** — `EventSource` **cannot set request headers**, so it cannot carry `Authorization: Bearer`; authenticating it forces a token-in-URL (leaks via logs/`Referer`) or a cookie (re-opens the CSRF surface). `fetch()`+`ReadableStream` sends the bearer header like every other route, so **one** auth mechanism covers the whole surface. It also lets us **drive reconnection + `Last-Event-ID` ourselves**: on stream error the SPA reconnects with `Last-Event-ID: <last seq>` as a header, and the server serves the gap from the **same `replay-from(seq)` ring/journal machinery** the editor↔Go channel uses (§2.5 step 7, §6.2). (Native `EventSource` auto-reconnect is convenient but re-introduces the header problem; we trade ~40 lines of JS reconnect logic for a single coherent auth+replay path.)
- **vs. WebSocket** — the observability stream is overwhelmingly **server→client**; control is low-frequency and one-directional (human→Go) and rides ordinary authenticated `POST` routes. WebSocket would force us to reimplement reconnection + replay on a second protocol and add an upgrade handshake for no benefit.
- Frame thumbnails are **not** inlined into the stream (which would bloat it); each `capture.frame`/`op.thumbnail` event carries a `seq`, and the SPA lazy-loads the image from an authenticated `GET /frame/<seq>` (or a `data:` URI for small thumbs). The full-res frame is fetched on demand.
- The **TUI** does not use SSE at all; it attaches to the same in-process cockpit state over the daemon.

**Security — this is a local *control* surface for destructive-op approval and editor Force-kill, so it is authenticated, not merely loopback-bound.** A loopback-only web endpoint is still reachable by *any* local process and is CSRF-able by *any* browser page the human visits (a bare `POST /stop` needs no CORS read). Three layers close this:

1. **Per-session capability token on every route.** The **same token** `cockpit_info` mints (§2.5) is required on **all** routes — the streaming `GET /events` (now via the `fetch()` bearer header, above) *and* every state-changing `POST` — as an `Authorization: Bearer <token>` header. The token is delivered to the SPA in the **URL fragment** (`http://127.0.0.1:<port>/#<token>`) so it is never sent as a `Referer` or written to server logs; the SPA reads `location.hash`, stores it in memory, and immediately clears it. No token ⇒ `401`. This stops a co-resident local process from passively siphoning the agent's activity *or* driving control routes.
2. **Origin/Host allowlist (defeats DNS-rebinding and cross-origin CSRF).** Every request is rejected unless its `Host` header is `127.0.0.1:<port>` or `localhost:<port>` **and** (for requests that carry one) its `Origin` matches the cockpit origin. A DNS-rebinding attack points an attacker-controlled name at `127.0.0.1`, but the browser then sends that *name* in `Host` — which fails the allowlist. A malicious cross-origin page cannot set the `Authorization` header without a CORS preflight, which we reject (no permissive `Access-Control-Allow-*`) — so a drive-by `POST /stop` or `/force-kill` cannot succeed.
3. **State-changing routes are `POST`-only and non-simple.** Requiring a custom `Authorization` header makes every control request — and the `fetch()` event stream — a *non-simple* CORS request, forcing a preflight the server denies — belt-and-suspenders with (1)/(2). `GET` routes are read-only.

The token, Origin allowlist, and `401`/preflight-rejection behavior are covered by a Go test in `internal/cockpit` (§8.3) — an unauthenticated local control surface is treated as not shippable.

**Multi-editor layout (defines "one cockpit fronting N editors").** The daemon already routes N projects. The cockpit renders **one pane/tab per connected editor, keyed by `project + session_epoch`** (so a restart-with-new-epoch is visibly a new pane, not a silently-reused one). The header strip lists every connected editor with a per-editor status pip and BUSY indicator. **STOP is per-editor** — the big red button targets the *focused* pane's editor channel — and there is an explicit, separately-styled **STOP ALL** that fans a stop out to every connected editor. Each STOP's in-browser ack (< 100 ms) is per-target, so "which editor did I just stop" is never ambiguous. Force-kill (§4.5) is likewise per-editor and always behind a confirm.

**Phase-A1 gate measures end-to-end to the browser.** The "STOP ack < 100 ms" number is measured **from the human's click in the rendered SPA to the rendered acknowledgment** (POST round-trip to Go + SSE echo to the DOM), using a synthetic headless-browser client — not merely to the Go process boundary. If the browser had to *poll*, the instant-ack claim would be a lie; the `fetch()` stream + the < 100 ms end-to-end gate makes it honest and falsifiable (§8.1).

### 3.3 The secondary in-editor surface — a thin status strip now, richer panel deferred

**Decision: native Slate, kept deliberately thin in Phase A (gamedev minor).** Because the primary surface is out-of-process and any in-editor panel is dark during ops and merely mirrors Go-side state between ops, building a full Slate module (virtualized feed/log lists, `FMessageLog` page, filmstrip) in Phase A is a large net-new cost for a strictly-worse mirror. So Phase A1's `MCPCockpit` ships only a **thin status strip**:

- a toolbar **STOP** button that routes through Go (so it shares the always-live control path, not a separate in-editor code path),
- a **connection-status pip** (color-blind-safe) showing connected/agent-driving/disconnected,
- an **"Open cockpit (http://127.0.0.1:port)"** button that launches the primary surface.

Phase C adds **actionable approval toasts** to this module (inline Approve/Deny via `FNotificationInfo::ButtonDetails`, §4.2) so a human working in the editor can decide a gate without alt-tabbing — the *only* richer in-editor surface pulled forward, because approval latency is an ergonomics blocker. A docked feed/log/filmstrip mirror remains **deferred to Phase D and gated on real demand.** If we build it, it is native Slate (an EUW is Blueprint-asset-backed content, can't cleanly own a socket, and reads as a dev hack), and it only ever *reads* Go-side state and issues control — the socket/dispatch/`FOutputDevice`/ring stay in `MCPCore`.

**Registration lifecycle — deferred, consistent across §3.3/§2.7 (fixing the first draft's contradiction and first-boot race).** Even the thin strip is **not** registered from raw `StartupModule` (which races `LevelEditor` module load — a known footgun). It is registered on **`FLevelEditorModule::OnTabManagerChanged` / post-engine-init**, funneled through `UToolMenus::RegisterStartupCallback` so menu extension and any tab registration happen together after the level editor exists. Mechanism: toolbar + Window-menu entries via `UToolMenus` (`RegisterMenu`/`AddMenuEntryObject`, `ToolMenus.h:161/:205`) extending `LevelEditor.LevelEditorToolBar` / `LevelEditor.MainMenu`, owned by an `FToolMenuOwnerScoped` (`:531`) for clean teardown; if the deferred panel lands in Phase D it registers a nomad tab via `FGlobalTabmanager::Get().RegisterNomadTabSpawner` (`TabManager.h:1499`) opened by `TryInvokeTab` (`:1049`). Every entry point is guarded on `FSlateApplication::IsInitialized()`.

A long op raises the inline **EDITOR BUSY** row (§2.6) that keeps updating while the editor is frozen. **Gate rows render inline with the before→after diff and Approve/Deny/Focus actions (§4.2).**
- **State panel** (switchable):
  - **World/PIE** — current map, editor-vs-PIE world, PIE run state, client count, elapsed (from PIE/map delegates, §6); **held injected-input** — the live set of keys/axes the agent is holding via `MCPControlSubsystem` (`input.held`, §6.1), with a distinct **"input released"** confirmation when `ReleaseAll` fires (`input.released`), so a human always knows if the agent left a key stuck (fix #12).
  - **Selection** — selected actor labels from `USelection`, live via `SelectionChangedEvent`, attributed human-vs-agent (§4.3), and **anchored to the human's selection** (§4.4) so agent churn doesn't whip it around.
  - **Packages/SCC (fix #4)** — a live "**N packages modified — M dirty / K saved this session / J checked-out**" panel, driven by `UPackage::IsDirty()` + `ISourceControlProvider` state (§5.2), listing which packages the *agent* dirtied/saved/checked-out this session, with the provider name (Git here). This makes the agent's on-disk / source-control footprint legible before the human commits or reverts.
  - **Logs** — filtered, virtualized view of the engine output-log stream captured by our `FOutputDevice` (§6), verbosity per `UMCPSettings`.
  - **Issues** — structured, dismissible diagnostics.
  - **Frame** — the captured-frame + per-op editor-thumbnail filmstrip (§3.5).
  - **Perf** — source-labeled and honest (§3.6).
- **Control bar** — Pause / Step / Resume, approval-policy dropdown, and the escalating **STOP** (§4.5). Pending-approval **gate rows** render inline with Approve/Deny, the **before→after diff**, a **"Focus in editor"** action, and the `args_hash` the human is approving (§4.2).

### 3.5 "What the agent sees" — the actual frames, plus a per-op editor thumbnail (fix #5)

For a visual medium the single most legible signal is *seeing the frame the agent acted on.* The `SceneCapture` pipeline and `capture.frame` events already exist, so:

- A **captured-frame filmstrip pane** renders the last N frames the agent captured, each driven by a `capture.frame` event and **tied to the op in the feed** that produced it (click a feed row → its frame; click a thumbnail → its op). On-demand editor-viewport grabs feed the same strip.
- **Auto editor-thumbnail per mutating op (fix #5).** Level edits are spatial, but a `spawn_actor {loc:[...]}` row is not — the human can't see *where* the agent just changed the world. So for each **mutating** op (or, coalesced, per `task_id`), `MCPCore` auto-captures a small **editor-viewport thumbnail framed on the op's target bounds**: it resolves the target's world-space bounds via `AActor::GetActorBounds` (or the asset's editor representation), positions an **editor-world SceneCapture** to frame those bounds, and emits an `op.thumbnail{op_id, seq}` event linked to the feed row. This turns "spawned ISMActor at [..]" into a picture of the actual change. **It is rate-limited, cost-budgeted, and retention-capped** (`UMCPSettings.ThumbnailMaxPerSec`, `ThumbnailFrameBudgetMs`, `FrameRetentionCount/Bytes`, §6.2/§7) so it never becomes a per-op render tax, and it is skipped entirely in `-nullrhi` (no RHI to capture) — the strip degrades to "no thumbnail (headless)" rather than erroring.
- **Optional "follow the agent" toggle (fix #5).** A cockpit toggle that, when on, **pilots the human's editor viewport to the agent's current target** (`ULevelEditorSubsystem::PilotLevelActor` / `GEditor->MoveViewportCamerasToActor`), so a human watching a guided edit rides along. **Off by default** and mutually consistent with selection stewardship (§4.4): follow-mode is an explicit opt-in to *let* the agent move the human's view, exactly parallel to `AgentMayChangeSelection`.
- This pane **lives on the Go-hosted primary surface**: the web SPA renders images natively (lazy-loaded from `GET /frame/<seq>`, §3.2); the TUI shows thumbnails/paths and opens full frames on demand.
- The **"what the agent sees" mirror** is redefined concretely as **the actual captured frames + the per-op editor thumbnails + the exact event/rpc frames** the agent's Go client received (same `seq`, same payloads). Because control and observation share one `seq` space, this mirror is *exactly* ordered relative to the action feed (fixing the split-brain ordering gap in ground-truth §5).

### 3.6 Perf panel — honest sourcing (no rebranded freeze artifact)

The second draft oversold a live "editor ~N ms/tick" derived from the cockpit's own `FTSTicker` frame-delta. That ticker doesn't run while the game thread is blocked, so it reads a healthy idle number between ops and then one giant delta for the blocked frame — never a live hitch curve. Corrected:

- **Idle cadence, labeled as such.** The in-editor ticker delta is shown as **"editor idle cadence (not valid during ops)"** — never a bare "0 FPS," never presented as a live per-op hitch.
- **The real stall signal comes from the Go side.** The Go server pings the editor and measures **heartbeat-gap** latency; when a Tier-P op holds the game thread, the Go surface reports the *actual* stall duration ("editor game thread stalled 1.9 s on `list_actors`") — a genuine signal the in-editor ticker cannot produce. This heartbeat-gap number is also the source for the published **p50/p99 Tier-P op durations** (§4.5). The **last-hitch cause** (shader compile / asset load) is read from the log stream.
- **During PIE** — game FPS / frame-ms / worst hitch from the game-thread tick / `stat unit`, labeled "game."
- **On demand** — a "Capture perf" button triggers the existing CsvProfiler/`memreport` path and parses it via `internal/perf` (which is verified offline CSV/dump parsing at `internal/perf/perf.go`, *not* live per-tick). That is the only place a genuine per-frame perf claim is made.

## 4. Human-in-the-loop control

The plugin owns dispatch, so the human's authority is real — within the game-thread limits of §2.6, with the gate/park loop owned by the Go client so the agent contract is preserved, and with **yield-to-human pacing** (§4.4) so the human's own editor never starves.

### 4.1 Pause / step / resume (the agent, and PIE)

Two independent axes:

- **Agent pacing** — a `control` latch in the dispatch core. **Pause** stops the core from *starting the next* rpc (an in-flight Tier-P op still runs to completion; only a chunked Tier-N op honors the cancel flag mid-way). The parked agent tool call is held open by the Go client with periodic progress (same mechanism as gates, §4.2) rather than returning a wedging error. **Step** admits exactly one queued op then re-latches. **Resume** clears the latch. (This manual latch is distinct from the *automatic* yield-to-human governor of §4.4, which throttles rate without a human pressing anything.)
- **PIE pacing** — Pause/Step/Resume of the running game via the editor's PIE control, *observed* via `FEditorDelegates::PausePIE/ResumePIE/SingleStepPIE` (`Editor.h:253/:255/:257`) so the cockpit reflects true state even when a human uses the stock toolbar.

### 4.2 Approval gates — inspect-then-approve, args-hash-bound, and bound to the call's lifetime

Every rpc is **classified** by the capability manifest (§5.3): `read` / `mutate` / `destructive` / `pie-control` / `build` / `scc` / `exec`. `UMCPSettings` holds a **policy** (e.g. *auto-allow read; gate mutate+; always gate destructive, scc & exec*). **Fail-closed:** an op with no classification is treated as `destructive+exec` and is always gated (§5.3).

**The gate must be a real inspection surface, must never hold the editor slot for minutes, must never change the agent's tool contract, and must never outlive the call that created it.** The second and third drafts got the first three progressively right; this draft closes the last two gaps the reviewers named — the gate as a *rubber-stamp* (fix #1) and the gate that can *outlive its call* (fix #3). Ownership of the park/re-issue loop is **`internal/cockpit` (Go), never the model:**

1. **Plugin — park, read the target, free the slot.** On a gated op the dispatch core, **on the game thread it already owns**, first **reads the target's current value(s)** for the pending mutation (for `set_property`/`set_editor_property`-class ops it reads the live property via `FProperty::ExportText_InContainer`; for destructive ops it records the target's identity + a one-line summary of what will be destroyed) and builds a **before→after `diff`**. It then parks the op, **immediately releases the single-flight editor slot**, and emits a `gate{gate_id, op, classification, args_hash, diff}` frame — where `args_hash` = a hash of `{op, canonicalized args}`. It waits out-of-band. *(This read is the whole point of owning game-thread dispatch: the human approves against the object's actual current state, not a blind arg blob.)*
2. **Go — hold the MCP call open, bound to its context.** `internal/cockpit` does **not** surface a new error to the model. It **keeps the agent's MCP tool call open**, emitting periodic MCP progress notifications ("awaiting human approval — N s elapsed"). The single-flight command slot is free, so other ops (or STOP) proceed. **The park is bound to the tool call's `context.Context` (fix #3):** if the MCP client disconnects or the call's context is cancelled while parked, Go **cancels the pending gate** (sends `control:cancel(gate_id)` so the plugin discards it) and the op is **never executed on a later Approve**.
3. **Human — inspect, then decide.** The Go cockpit shows an inline gate row with the **before→after diff** and (in the editor, Phase C) an **actionable toast** (`FSlateNotificationManager` with `FNotificationInfo::ButtonDetails` inline **Approve/Deny** buttons, coalesced under a burst so a flurry of gates becomes one grouped toast, §3.3) — so a human working *in* the editor never has to alt-tab to decide (fix #1c). Each gate row also offers **"Select/Focus target in editor" (fix #1b):** clicking it issues `control:focus-target(gate_id)`, and the plugin — **under the save/restore contract (§4.4)** — temporarily selects and pilots the viewport to the target (`GEditor->SelectActor` + `MoveViewportCamerasToActor`/`PilotLevelActor`), lets the human eyeball it, then **restores the human's prior selection and view** when the gate resolves or the human clicks "return." The gate row carries the agent's `intent` so the human approves against *why*, not just *what*. A "always allow this op this session" control tunes the policy live.
4. **Go — transparent re-dispatch on approve.** The plugin marks the gate approved (bound to `gate_id`+`args_hash`). The parked Go call re-dispatches the op **with the identical canonicalized args** (same `args_hash`), carrying `gate_id`. The plugin runs it and returns the op's **normal result** to the still-open tool call. The agent saw only a slower call.
5. **Deny / expire / abandoned.** **Deny** resolves `DENIED`; the parked call returns the op's normal error envelope with code `DENIED`. **Park timeout** (`UMCPSettings.GateTimeout`) → `EXPIRED` (treated as denied). **Abandoned (fix #3):** if the call's context was cancelled while parked and a human later clicks **Approve** on the now-orphaned gate, the plugin refuses to execute and the cockpit surfaces **`AGENT_SEVERED`** ("the agent that requested this is gone; nothing was executed") — so approving a stale gate can never fire an op into a world the requester no longer expects.
6. **GateTimeout is capped to a safe fraction of the call budget (fix #3).** `GateTimeout` (default 5 min) is **clamped at startup to a documented safe fraction (default 80%) of the effective MCP client / HTTP request timeout** so a parked gate can **never** outlive the call holding it open — the park always resolves (approve/deny/expire/sever) before the transport would abandon the request. The clamp and its inputs are shown in the cockpit and logged.
7. **TOCTOU defense.** The plugin binds approval to `args_hash`. Since Go re-dispatches its *own* parked args, the hashes match by construction; any re-issue whose args-hash differs from the approved gate is rejected with a distinct **`GATE_ARGS_MISMATCH`** — so "human approves X, Y executes" is impossible.

**Agent-facing contract (exact):**

| Situation | What the agent's MCP tool call observes |
|---|---|
| Gated, then approved | Held open with progress pings; then the op's **normal result**. |
| Gated, then denied | Held open; then the op's normal error envelope, code `DENIED`. |
| Gated, park timeout | Held open; then `EXPIRED` (denied). |
| Client disconnect / ctx-cancel while parked | Gate is cancelled; op **never runs**; the call is already gone (a later human Approve yields `AGENT_SEVERED`, surfaced to the human, not the agent). |
| Re-issue with different args under a `gate_id` (defense-in-depth) | `GATE_ARGS_MISMATCH`. |
| Not gated (policy auto-allow) | Unchanged — immediate normal result. |

This is only possible because dispatch is ours — today the editor executes whatever Python arrives, blind — and because the *Go* client, not the model, owns the park loop, the "agent contract unchanged" invariant is literally true.

### 4.3 Intervene / override, attribution, and the undo contract

It is the human's editor; they can always grab the mouse. The cockpit makes that safe **without** the first draft's broken heuristic and **without** the second draft's undo-stack pollution.

**Attribution — from an authoritative flag, not transaction provenance.** The first draft inferred "a transaction not from an in-flight op == human," but most Tier-P mutations (`set_editor_property`, direct field sets) open **no** `FScopedTransaction` and may emit **no** `OnObjectTransacted`, while a human drag does — so provenance could invert the attribution. The fix: the core exposes `IsMcpOpExecuting()` (true while any op runs on the game thread). A `SelectionChangedEvent`/`OnObjectTransacted` firing while that flag is **false** is human; while **true** it is the agent. This cannot invert, and it does **not** require transacting agent edits.

**Undo — the GUndo-ownership contract (fixing second-draft pollution, third-draft batch-lifetime, and — new — the redo-stack clobber).** The second draft wrapped every mutating Tier-P op in a server-side `FScopedTransaction` that landed in the *shared* `GUndo` buffer, so one human Ctrl+Z would eat 30 interleaved agent edits. The third draft coalesced agent edits into one labeled batch — but left the batch open across wall-clock seconds, during which a human Ctrl+Z is undefined/hazardous. Both are fixed here, and this draft adds the reviewer's missing honesty (fix #6): **every `BeginTransaction` on the shared `GEditor->Trans` (`UTransBuffer`) truncates the redo stack — so an agent edit silently destroys a human's ability to Redo.**

*Reconciling the reviewer's ideal with the public-API reality (explicit decision).* True per-author partitioning of the single shared interactive transactor (`GEditor->Trans` / `UTransBuffer`) is **not** a public-API capability — Ctrl+Z pops the most recent committed transaction regardless of author, there is no public "discard the top committed transaction without undoing it," and opening any transaction discards the redo queue. Hijacking or swapping the transactor to hide agent edits would corrupt the human's own history. So we adopt the reviewer's accepted alternative **(b)** — the cockpit is the authoritative agent-undo surface — **bound the batch's open lifetime, and explicitly steward the redo stack:**

1. **Coalesce into a labeled agent batch.** Consecutive agent mutations *with no intervening human edit* (via the `IsMcpOpExecuting()` signal above) are grouped into **one** collapsible transaction, labeled `MCP: agent batch (N ops)`. A human edit closes the current batch; the next agent mutation opens a fresh one. So one human Ctrl+Z reverts **at most one clearly-labeled batch as a single predictable step — never 30 interleaved steps.**
2. **Time-box and size-box the batch.** The batch is force-closed (`EndTransaction`) on the **first** of: **N ops** (`UMCPSettings.UndoBatchMaxOps`, default 20), **T ms of wall-clock** (`UndoBatchMaxMs`, default 750 ms), or a game-thread **yield to human input** — so the transactor is never left open across an idle gap where a human might Ctrl+Z. A fresh batch opens on the next agent mutation.
3. **A human undo/redo first closes the batch.** If a human undo/redo request arrives (via the editor, or routed through the cockpit) while a batch is open, the dispatch core **force-closes the batch before the undo executes.** A human Ctrl+Z therefore always operates on a *committed* transaction, never an open one — no assert, no dead key.
4. **Redo-stack stewardship (fix #6).** Because opening an agent transaction clears the human's redo stack, the core **checks `GEditor->Trans->CanRedo()` before opening the next agent batch: while the human has a non-empty redo stack, it defers opening a new batch** (holding the agent's next mutating op under the pacing latch of §4.4) so the agent does not silently eat a Redo the human may be about to use. When deferral is not possible (e.g. the agent must proceed), the cockpit **warns explicitly** ("agent edit will clear your redo history") on both surfaces before the batch opens. The deferral window is bounded (a `UMCPSettings` timeout) so the agent is never blocked indefinitely; the default trades a short agent delay for not destroying human redo state. This limitation — that agent work and human redo cannot fully coexist on one shared transactor — is named plainly rather than hidden.
5. **Never double-wrap self-transacted ops.** Several Tier-P/Tier-N bodies already open their own transactions (e.g. `UEditorActorSubsystem` spawn/duplicate/delete). The manifest carries **both** a `mutating` bit *and* a `self_transacted` bit; the dispatch core wraps *only* `mutating && !self_transacted` ops, and absorbs self-transacted ops into the batch grouping via `BeginTransaction`/`EndTransaction` boundaries rather than a nested `FScopedTransaction` (no nesting, no double labels).
6. **The cockpit owns authoritative agent-undo.** Because the interactive buffer cannot be author-partitioned, the primary way to revert agent work is the cockpit's **"Undo last agent op" / "Undo agent batch"** controls, which step the agent batch granularly (backed by the batch transaction + the journal). The human's Ctrl+Z remains theirs, bounded to one labeled batch.
7. **Policy toggle.** `UMCPSettings` selects `coalesced-batch` (default), `off` (no agent transactions — and thus no redo clobber), or `per-op`.

**The stated contract:** *a human Ctrl+Z after an agent batch reverts at most one labeled, collapsible agent batch as a single step (never a storm of interleaved agent edits); the batch is never open across an idle gap or a human undo/redo request (time/size/yield-boxed, force-closed before a human undo), so a human Ctrl+Z is never dead or unsafe; the agent defers opening a new batch while the human has a pending Redo (or is warned), because a new transaction clears the redo stack; the cockpit's "Undo agent" control is the primary, granular agent-undo path; self-transacted ops are never double-wrapped.* Gated in Phase C.

**Take-over** — one click latches the agent, releases any injected input (`MCPControlSubsystem::ReleaseAll`, surfaced as `input.released`, §3.4), and hands the editor to the human; the agent's parked calls hold until resumed.

### 4.4 Co-working: yield-to-human pacing, concurrency, selection stewardship, and asset-level conflict

Attribution classifies *who did what*; it does not stop the agent from *freezing the human's hands*, *conflicting* with a human edit, *stealing the human's selection*, or *recompiling an asset the human has open*. Four contracts, all `UMCPSettings`-governed.

**Yield-to-human pacing (fix #2 — the co-working guarantee).** The flagship promise is "the dev works while the agent works." That is false if a stream of agent ops monopolizes the game thread, because the human's own drag/select/edit also needs it. So the dispatch core is **human-input-aware**:

- **Detect active human interaction.** Between ops the core reads `FSlateApplication::Get().GetLastUserInteractionTime()` and whether a viewport or details panel currently holds keyboard/mouse focus (`GetUserFocusedWidget`). If the human interacted within a recent window (`UMCPSettings.HumanActiveWindowMs`, default 1500 ms) or holds an editing widget focus, the human is "active."
- **Throttle agent ops while the human is active.** The core inserts a **yield/rate-limit between agent ops** — a governor capping agent dispatch to `UMCPSettings.MaxAgentOpsPerSecWhileHumanActive` (default e.g. 4/s) — so the game thread reliably returns to the human between agent ops. When the human is idle, the governor lifts and the agent runs at full speed. This does **not** and cannot shorten a single in-flight Tier-P op (§2.6); it bounds how *often* the agent seizes the thread, which is what makes the editor feel responsive under a co-working load.
- **Parked, not failed.** A throttled op is held under the same Go-side park (no `PENDING`/error to the model), so pacing is invisible to the agent except as slightly slower calls while the human is hands-on.
- **Interaction with §4.3(4):** the redo-deferral window also rides this latch, so "wait for the human's Redo window" and "yield to active human input" share one mechanism.

This is the concrete delivery of §1.1's co-working framing: not merely honest about the freeze, but actively giving the human game-thread cycles.

**Concurrency.** The scary daily case is the agent mid-batch while the human grabs the mouse and deletes/edits the actor the agent is about to reference.

- **Non-modal "agent is editing" indicator.** While an agent op is in flight, the cockpit (both surfaces) shows a non-modal indicator; the in-editor strip surfaces a subtle pip between ops.
- **Identity re-resolution + a distinct `CONFLICT` code.** Mutating ops **re-resolve their targets by stable identity at execution time** (actor GUID / object path, not a stale pointer or label captured when the op was issued). If the target changed or vanished since the op was issued, the op **fails with a distinct `CONFLICT`** code — never a silent corrupt or a write to the wrong object.
- **Asset-level concurrency + `ASSET_OPEN_IN_EDITOR` (fix #7).** The `CONFLICT` model is extended from actors to **assets**: before a mutating/compile op touches an asset (Blueprint compile, asset property write, reimport), the core calls **`UAssetEditorSubsystem::FindEditorsForAsset(asset)`**; if the human has that asset open in an editor, the op is **gated `ASSET_OPEN_IN_EDITOR`** (surfaced with the asset name + "you have this open") or, under the soft-lock toggle below, soft-locked — so the agent can **never silently recompile a Blueprint the human is editing** and blow away their unsaved graph changes. The human can Approve (proceed anyway), Deny, or switch to the asset first.
- **Optional soft lock.** A human-overridable "agent is mid-op — your edit may conflict" soft lock on the agent's current target selection and on assets open in an editor; the human can override with a one-click warning acknowledgment. Off by default, a `UMCPSettings` toggle that also governs whether `ASSET_OPEN_IN_EDITOR` soft-locks vs. gates.

**Selection stewardship (the flip side of the §6.2 property-scope decision — co-designed).** A dev who lives in the editor is enraged by tools that steal their selection. Agent ops inherently churn it (spawn/duplicate select the new actor; native select/deselect, §5.2), and because property observation is selection-scoped (§6.2), that churn also whips the observation window around — two coupled problems. The contract decouples them:

- **Default: save and restore the human's selection.** An agent op that does **not** semantically require a selection change (i.e. everything except an explicit `select_actors`/`focus_actors`, and the gate "Focus in editor" action of §4.2) **saves the human's prior selection before the op and restores it after** (on the game thread). So a spawn/duplicate no longer leaves the human staring at the agent's new actor.
- **Property observation is anchored to the *human's* selection, not the agent's transient reselection.** `property.changed` scope (§6.2) tracks the **human-established selection set** (the selection when `IsMcpOpExecuting()` is false) plus explicit `watch` targets — it is **not** repointed by an agent op's transient reselection.
- **Toggle.** `UMCPSettings.AgentMayChangeSelection` (default **false = restore**). Set true for sessions where the human *wants* to follow the agent's focus — the same intent as the §3.5 "follow the agent" viewport toggle.

### 4.5 Stop-switch — instant Go-side ack (< 100 ms), then categorized escalation

The big red **STOP** is safe to press *because the ack does not depend on the editor.* The Go server produces the ack the instant the human clicks — even while a Tier-P op holds the game thread. Each subsequent step is tagged by where it fires, **with a concrete budget:**

0. **Instant ack — [Go-side, in-browser < 100 ms].** The Go cockpit immediately shows: *"STOP received — no new ops will start; editor game thread busy with op X for N s; Force-kill available in T s."* No editor round-trip. Measured end-to-end to the rendered SPA (§3.2), not just to the Go process. This is the fix for "the STOP button can't repaint" — it lives on the unblocked surface.
1. **Sever the control plane — [off-thread, < 50 ms].** Latch closed; reject queued rpcs with `CANCELLED`; refuse new rpcs (agent parked calls return `AGENT_SEVERED`). Immediate on the rx thread.
2. **Cancel chunked work — [off-thread, < 50 ms].** Set the cancel flag; any chunked Tier-N op polling it stops between chunks. A monolithic Tier-P op does **not** stop here.
3. **Cancel Go-side jobs — [off-thread, Go, < 50 ms].** The client signals any async subprocess (build/cook/long capture, §2.6 rule 1) to cancel. This is where "kill a long op" actually lives.
4. **Release input — [game-thread, deferred].** `MCPControlSubsystem::ReleaseAll()` (no stuck keys, surfaced as `input.released`, §3.4), on the next tick the game thread yields.
5. **End PIE — [game-thread, deferred].** `GEditor->RequestEndPlayMap()` if a session is running, on the next tick.

**The honest deferred-STOP model (gamedev major, retained).** Steps 4–5 fire on the game thread, so their latency = **the in-flight op's remaining game-thread time**, which is **unbounded in principle** (asset walks, blueprint compiles, `pie_observe` run many seconds — the mockup's `list_actors` is 1.9 s). We do not pretend otherwise. Instead:

- The cockpit's BUSY banner shows the *live elapsed* of the blocking op, so the human sees exactly how long the deferred effect is waiting on.
- We **publish measured p50/p99 Tier-P op durations from a real session** (sourced from the Go heartbeat-gap signal, §3.6) in the docs and the Phase-C gate, so "how long until my STOP releases injected PIE input" has an empirical answer, not a hand-wave. Seed value: `list_actors` ≈ 1.9 s in the reference mockup session; the gate publishes the real distribution.
- **Force-kill is offered after a concrete timer `T`** (`UMCPSettings.ForceKillOfferSeconds`, default **10 s**) of a STOP-pending game thread that has not yielded.

**Last-resort hard-kill (explicit, realistic guarantee):** if the game thread never yields (a pathological Python op wedged in an infinite loop), no in-process action can run — a physical limit. The honest last resort is Go-side: the daemon can **terminate the editor process** (`internal/lifecycle` owns liveness/teardown; `Kill(pid)` verified at `lifecycle.go:67`). We state this plainly as the only guaranteed stop for a wedged game thread, gated behind an explicit **per-editor** "Force-kill editor" confirmation in the cockpit (offered on the `T`-second timer after STOP, per step 0), noting it loses unsaved state (the journal's last-gasp marker, §4.6, bounds the audit trail).

Steps 0–3 fire **while a long op holds the game thread**; steps 4–5 are honestly deferred to the next yield.

### 4.6 Audit & replay trail

Every op is journaled: channel, op name + args, **intent/task_id**, classification, result/error, timing, the human approval decision (auto/approved/denied/expired/**severed**) **and the approved `args_hash` + the gate diff**, originating agent/session, `session_epoch`, **package/SCC effects (dirtied/saved/checked-out)**, and event `seq` bracket. Two sinks:

- **Durable** — append NDJSON to `<Project>/Saved/MCP/journal.ndjson`. **Path decision (reconciling the drift):** a **net-new superset** file in the existing `Saved/MCP/` tree (already home to `Saved/MCP/capture`). It does **not** move or replace the Python-fallback stream at `Saved/PyMCP/events.ndjson`, which `internal/events` (byte-offset tail, verified `events.go:25/:41`) and the uexec path keep using unchanged — no lockstep breakage. The two coexist. The journal is **size/age-rotated** (`UMCPSettings` retention, §6.2/§7) so an all-day session cannot grow it without bound — asserted by the 8 h SOAK gate (§8.1).
- **Live** — the cockpit feed + the pushed event stream. It is the **replay** source: the cockpit can scrub the session; Go requests `replay-from(seq)` after reconnect (from the ring, then from `journal.ndjson` beyond it — the state machine in §2.5 step 7); and the **`fetch()`-stream `Last-Event-ID` browser reconnect** (§3.2) hits the same replay path.

An `FCoreDelegates::OnHandleSystemError` hook flushes a last-gasp journal marker on fatal error, so the audit trail has a definite end even on a hard crash. Crash *analysis* stays Go-side (`internal/crash` reading `Saved/Crashes/*`) — the in-editor journaler dies with the editor.

## 5. Complete control surface

### 5.1 Two implementation tiers, one dispatch table — and exactly how results come back

Every op is invoked identically by the agent (`rpc` frame, op name, base64/JSON args, same `OpError` envelope). Under the hood each op is either:

- **Tier P (Python-in-process)** — the op *body* is the existing `mcp_bridge.py` `_OPS[op]`, executed **in-process** via `ExecPythonCommandEx`. The default and the bulk of the surface.
- **Tier N (native C++)** — reimplemented natively where Python is *impossible* (input injection, game-world capture) or where latency/robustness/cancellability demands it (PIE control, save, transactions, build triggers, chunked batch ops). Same table, same manifest.

*(A third case — arbitrary-exec ops that bypass `_OPS` entirely — is handled separately in §5.5.)*

**How C++ gets the JSON back (the mechanism the first draft never specified).** `ExecPythonCommandEx` only yields a real return value in `EvaluateStatement` mode, where `CommandResult` is the *repr string* of the evaluated expression (verified against `PythonScriptTypes.h`: *"On success, for EvaluateStatement mode this will be the actual result… and will be None in all other cases"*). Repr-quoting a large JSON blob is fragile. So we do **not** rely on `CommandResult`:

- **Native result callback (chosen).** `MCPCore` exposes `UMCPCockpitBridge` — a `UCLASS` with a `UFUNCTION` reachable from the `unreal` module — e.g. `unreal.MCPCockpitBridge.emit_result(op_id, json_str)` and `emit_event(op_id, etype, json_str)`. It is a **thin forwarder** into the process-lifetime transport singleton (§2.7), so a Live-Coding reinstance of the bridge object does not lose the socket/ring. The **only** change to `mcp_bridge.py` is the emit sink on `_emit(payload)` (`:63`) and `_emit_event(etype, data)` (`:2479`): when a native sink is active for the *current dispatch* they call `emit_result`/`emit_event` with the **exact JSON bytes**; otherwise they fall back to the `__MCP_JSON__` marker `print` + `Saved/PyMCP/events.ndjson` append (the untouched uexec path). No repr, no stdout scrape, exact bytes.
  - **Routing is per-dispatch, NOT presence-tied (fix — decoupled).** The native-sink signal is threaded through the single guaranteed-`_emit` entry point — `_mcp_dispatch(op, b64args, op_id)` (verified the sole dispatcher, `:2802–2824`) — and set **only when `MCPCore` itself drives the call**. It is deliberately *distinct* from the `cockpit_info` presence probe below: a session where `MCPCore` is loaded but the transport fell back to uexec (e.g. the hello timed out) must keep marker-scraping stdout, so a presence-tied global would mis-route `_emit` to the native ring and hang. Threading the sink through the one dispatcher is a single-signature change, zero per-op edits. **Belt-and-suspenders:** `emit_result` also prints the marker when no framed peer is connected, so a mis-set flag degrades to the recoverable uexec path rather than a lost result.
- **Completion reconciliation — an rpc ALWAYS terminates (fix #10).** `ExecPythonCommandEx` is **synchronous**: the dispatch core calls it on the game thread and gets control back when the Python op returns, with a `bool bCommandSuccess` and a `TArray<FPythonLogOutputEntry> LogOutput`. But a well-behaved op emits its result *from inside* Python via `emit_result(op_id, …)`. If an op raises before it reaches `_emit`, throws in native binding code, or exits a path that never calls the sink, `emit_result(op_id)` **never fires** — and without reconciliation the rpc would hang forever. So **after `ExecPythonCommandEx` returns, the core checks whether `emit_result(op_id)` fired for that `op_id`; if it did not, the core synthesizes a terminal envelope itself** — `{ok:false, code:"EDITOR_EXEC_FAILED", error:<summary>}` — carrying `bCommandSuccess` and any `Error`-type `FPythonLogOutputEntry` lines as the traceback. Every `op_id` therefore reaches exactly one terminal state (a real `emit_result`, or this synthesized failure), so **no rpc can silently hang** on a Python op that died without emitting. This reconciliation is unit-tested against the `fakeeditor` (an op that deliberately never emits ⇒ `EDITOR_EXEC_FAILED`), and is a B1 gate.
- **`cockpit_info` is a SEPARATE presence probe (§2.5):** it reports whether `MCPCore` is loaded (a distinct signal from the per-dispatch sink flag above); absent ⇒ the `not_present` sentinel. Presence gates *backend selection*; the per-call sink flag gates *result routing* — decoupled so the two can never disagree into a hang.
- **Which functions change:** `_emit` and `_emit_event` only (~15 lines total, one `_MCP_NATIVE_SINK` check). Every `_op_*` body is untouched. This is what §2.1 means by "reuse the bodies, change only the sink."

**Text-op (`CallText`) parity — scoped honestly.** Today `CallText`/`FormatOutput` reconstruct op text from captured log entries (`bridge.go` `formatEntriesExcludingMarker`, keyed on `uexec.OutputEntry{Type: Info/Warning/Error}`). In-process, those lines arrive as `FPythonCommandEx::LogOutput` — a `TArray<FPythonLogOutputEntry>` with `Type ∈ {Info,Warning,Error}` + `Output` (verified in `PythonScriptTypes.h`). We define the mapping: `FPythonLogOutputEntry{Type,Output} → uexec.OutputEntry{Type,Output}`, filtering the marker line (now absent under the callback). **Gate scoping:** Phase B1's parity gate covers **structured (`Call`/JSON) ops** with an empty diff — well-defined via the callback. **`CallText` parity is a separately-gated follow-on** (log-verbosity/formatting differences validated then), not a B1 blocker.

### 5.3 The capability / affordance manifest — fail-closed, conformance-tested, code-reviewed (retained blocker)

The entire HITL safety story hinges on every dispatchable op carrying **correct** classification bits: the gate reads `category`/`mutating`/`destructive`/`scc`; the transaction-batch decision reads `mutating && !self_transacted` (§4.3); STOP's mid-op-cancel expectation reads `cancellable`; asset-conflict reads whether the op targets an asset (§4.4). But the op *bodies* live in `mcp_bridge.py` while the classification is authored separately — so a new op the classification table doesn't know about, or that silently defaults to "read/non-mutating," would **bypass the destructive-approval gate.** For a tool whose whole pitch is "trust the agent because the human gates the dangerous ops," that is a trust-destroying, safety-critical failure mode. Closed three ways:

1. **The classification table lives in `MCPCore` C++ and is the security boundary.** It is a compiled, versioned, code-reviewed table keyed by op name — `{name → category, mutating, self_transacted, destructive, cancellable, requires_pie, scc, touches_asset}`. It is **not** in `mcp_bridge.py` (which is hot-loaded content), because the thing that decides "gate this or not" must be reviewed and stripped as the security surface it is. The published manifest (below) is *generated from* this table. PRs that touch it are reviewed as security-sensitive.
2. **Fail-closed default.** Any op the dispatch core is asked to run that has **no explicit entry** in the classification table is treated as **`destructive + exec` — always gated, and never auto-batched.** A forgotten classification therefore fails *safe* (an extra approval prompt), never *open* (a silent destructive write). This is the single most important safety invariant in the plan.
3. **A bijection conformance test, wired into the B2 gate.** A test asserts **every `_OPS` key in `mcp_bridge.py` has a classification entry, and every classification entry maps to a real `_OPS` key** — no orphans on either side. It runs on **both** sides: a Go test (enumerating the op names via a tiny `list_ops` introspection op / the merged manifest) **and** a C++ `FAutomationTestBase` spec (against the compiled table). Adding an op to `mcp_bridge.py` without classifying it **fails CI** *and* is caught fail-closed at runtime — two independent nets. This is a hard gate in Phase B2 (§8.1).

On handshake the plugin publishes the **machine-readable manifest** generated from the table: `{name, tier(P|N), category, mutating, self_transacted, destructive, cancellable, requires_pie, scc, touches_asset, args_schema, since_epoch}` (digest carried in `welcome`, §2.5). It **replaces `hasattr` presence-sniffing** with explicit, versioned discovery; **drives the approval policy** and the batch decision; and **feeds the agent's discovery** (Go merges it with the Python op table and `internal/affordances` into one surface).

### 5.4 Backend selector — strictly exclusive, single owner, one-way fallback

Retaining uexec as a live fallback while the cockpit also dispatches in-process means two subsystems could otherwise race on bridge install/version. We forbid that:

- **Single owner of bridge install/version.** `internal/bridge` remains the *only* installer/version-asserter of `mcp_bridge.py` (`_MCP_BRIDGE_VERSION`). Neither backend re-installs behind the other.
- **Exactly one backend per session.** The selector picks native or python and **forbids concurrent dispatch across backends** against the same editor.
- **Cutover semantics.** On selecting native, any in-flight uexec op is **drained to completion or rejected** before the native channel accepts rpcs; the bridge version is **re-asserted once** on the winning channel. Atomic from the agent's view.
- **Fallback trigger, one-way.** If `cockpit_info` returns the **`not_present` sentinel** (native module absent, §2.5), or `hello` does not complete within `N` seconds (default 5), the session falls back to uexec/Python. **Fallback is one-way for the session** — no mid-session flapping. A commandlet host with no cockpit always uses the fallback.

### 5.5 Arbitrary-exec ops — the introspection hole, named and contained (retained blocker)

Two tools let the agent run arbitrary code that **sidesteps the `_OPS` dispatch table entirely**, so they sidestep classification, gates, and undo-batching unless we treat them specially. This is verified, not hypothetical: `execute_python` and `execute_console_command` are Go-side MCP tools (`register.go:68/:72`) whose handlers call `b.RunPython`/`b.Eval` **directly** (`handlers.go:19/:42`) — the code comment itself calls `execute_python` "the arbitrary-code escape hatch: it does not route through the companion dispatch table." A dev who set policy to "gate destructive ops" would be blindsided that the agent can `execute_python("...destroy_actor(...)")` with **zero gate**, and that mutations performed *inside* that Python never appear as classified feed rows and are never absorbed into the agent-undo batch. Closed:

- **Classified `exec`, always gated by default.** In the native cockpit, `execute_python`/`execute_console_command` are routed through the dispatch core as first-class `exec`-category ops (not the raw `RunPython` bypass), so the manifest classification applies and — under the default policy — **every raw exec is gated** before it runs. Combined with the fail-closed default (§5.3), an unclassified arbitrary-exec path can never be silently auto-allowed.
- **One opaque feed row, one agent-batch transaction.** The cockpit surfaces a raw exec as a **single "arbitrary exec" feed row** (showing the code/command and the agent's `intent`), and its dispatch is wrapped in **one** agent-batch transaction (§4.3) so a human Ctrl+Z reverts the whole exec as one labeled step.
- **The honest limitation, stated.** Mutations performed *inside* arbitrary Python (e.g. a script that spawns 40 actors and deletes 10) are **not individually classified, gated, or undo-batched** — we cannot introspect them without executing them. The plan says so plainly: raw exec is a *single* gated, *single* undo-batched, *opaque* operation; its internal effects (including any SCC/asset side effects) are the price of an escape hatch.
- **Hard mode.** `UMCPSettings.AllowRawExec` (default **on**) — when **off**, `execute_python`/`execute_console_command` are **denied outright** (not merely gated) for high-trust-required sessions. The agent receives a clean `EXEC_DISALLOWED` error.

### 5.6 RPC concurrency & queueing — one serialized slot, bounded queue, honest head-of-line (fix #9)

The dispatch model is stated explicitly rather than implied, because it is the concrete reason several other rules exist:

- **Tier-P is strictly serialized on the game thread — exactly one op executing.** `ExecPythonCommandEx` binds the GIL and asserts on `GEditor`/UObjects (§2.6); the game thread runs **one** Tier-P op at a time. There is no parallel Python dispatch, by construction.
- **rpcs queue with a bounded depth `D`.** Incoming `rpc` frames beyond the executing op are enqueued in a **bounded FIFO of depth `D`** (`UMCPSettings.RpcQueueDepth`, default e.g. 8). Chunked Tier-N ops and native ops share the same single-slot serialization on the game thread (they marshal onto it); only Go-side async subprocesses (§2.6 rule 1) run off it.
- **Beyond `D`, reject with a distinct code.** A frame arriving when the queue is full is rejected immediately (off-thread, on the rx thread) with **`QUEUE_FULL`/`BUSY`** — a distinct, retryable `OpError`, never a silent drop and never an unbounded backlog. The agent (a single-flight MCP client in practice) rarely hits this, but a burst or a second agent will get a clean back-pressure signal.
- **Head-of-line blocking is acknowledged, not hidden.** While a long Tier-P op holds the single slot, every queued rpc waits behind it — that *is* head-of-line blocking, and it is **the concrete reason long work MUST run Go-side-async** (§2.6 rule 1): a build or long capture placed behind the slot would stall every other op and every deferred STOP step (§4.5). The queue depth `D` bounds how much can pile up; the async rule prevents anything long from being in the slot in the first place.
- **STOP interaction.** On STOP, queued rpcs are rejected `CANCELLED` (§4.5 step 1) and no new op is admitted; only the one already-executing Tier-P op runs to its yield. So the queue never *extends* a STOP's deferred latency beyond the single in-flight op.

This subsection is asserted by the `fakeeditor` tests (queue fills → `QUEUE_FULL`; STOP drains the queue with `CANCELLED`; exactly one op executes at a time) and is a B1 gate.

### 6.2 From poll to push — bounded, lossy, wait-free, storm-safe, and cost-capped

Each event carries `{seq, t_wall, t_engine, type, payload}` with a **monotonic `seq`**. The bus is a **bounded MPSC ring**, drained by the socket worker and pushed as `event` frames (and, for the browser, re-emitted over the `fetch()` SSE stream with the `seq` as the SSE event id, §3.2).

**Wait-free producers (fixing the FCriticalSection-contention gap, per eng10x).** The second draft guarded enqueue with a single `FCriticalSection`, but `FOutputDevice::Serialize` is hit **concurrently by many worker threads** during a shader-compile log storm — they would contend on that one lock, so "producers never block" was not literally true. Corrected: **per-thread staging.** Each producing thread writes into a small thread-local staging buffer (no shared lock on the hot path); a single drain step folds staged records into the ring on the drain tick. The `Serialize` path is therefore **wait-free** (or at worst a bounded, uncontended CAS on hand-off). We downgrade the literal claim to "**producers never block beyond a bounded, uncontended hand-off**," and the BUSY load test **asserts worst-case enqueue latency under N contending threads** (not merely "ring stays bounded").

**The backpressure policy (stated, and load-tested as a Phase-A gate — §7/§8):**

- **Drop-oldest, never wait.** On a full ring — or a slow Go socket consumer — the producer **drops the oldest** entries and never waits.
- **Loss is observable and repairable.** When drop-oldest fires, the bus emits a `dropped{count, from_seq, to_seq}` marker. The cockpit shows "dropped N events," and the Go client detects the `seq` gap and issues **`replay-from(seq)`** — served from the ring, then **beyond the ring from `journal.ndjson`** (the durable floor). Replay-from(seq), the `fetch()`-stream `Last-Event-ID` reconnect (§3.2), and drop-oldest are one integrated mechanism (the state machine in §2.5 step 7).

**Storm guards at the source (fixing the property-change firehose, per gamedev):** `OnObjectPropertyChanged` fires for *every* property change on *every* UObject — a details-panel slider drag fires it continuously; a map load / asset import / construction-script run fires it thousands of times across thousands of distinct objects, so per-object-per-tick coalescing does **not** bound it (the object *count* is the problem). Therefore:

- **Scope: the human's selection + explicit watch-targets, by default (co-designed with §4.4).** `property.changed` is observed only for the **human-established selection set** (the selection when no agent op is executing) and explicit watch targets — **not** globally, and **not** repointed by an agent op's transient reselection. Global observation is an opt-in `UMCPSettings` toggle for advanced debugging.
- **Hard per-tick emission cap.** At most `N` `property.changed` events per tick (a `UMCPSettings` cap); on overflow, emit a single **`property.changed.truncated{count}`** marker instead of the tail.
- **Bulk-phase suppression.** During known bulk phases — map load, asset import, PIE transition, `SaveDirtyPackages` — the `property.changed` family is **suppressed entirely**, bracketed by the map/save/import/PIE delegates, and replaced by a **single summary event** (`property.bulk{phase, object_count}`) at phase end.
- **Same for camera/selection** — coalesced per-object per-tick as before; the cap/scope apply.

**Capture cost caps (fix #11).** The captured-frame filmstrip and the per-op editor thumbnail (§3.5) are bounded so an all-day session cannot grow memory/disk or tax rendering:

- **Rate-limit.** At most `UMCPSettings.ThumbnailMaxPerSec` op-thumbnails/sec; a mutating-op storm coalesces to per-`task_id` (one thumbnail per task, not per op).
- **Per-frame cost budget.** Each editor-thumbnail capture must fit `UMCPSettings.ThumbnailFrameBudgetMs`; if the game thread is over budget the capture is **skipped** (the feed row shows "thumbnail skipped — busy") rather than added to the hitch.
- **On-disk retention cap.** Frames are retained under a ring by both **count and bytes** (`UMCPSettings.FrameRetentionCount` / `FrameRetentionBytes`); the oldest are evicted; `GET /frame/<seq>` for an evicted frame returns a clean 410, and the SPA shows a placeholder.

These cap the ingress rate so the ring rarely saturates, and cap the on-disk/render cost so the SOAK gate (§8.1) can prove no unbounded growth. **Diagnostics:** per-family counters (produced, coalesced, dropped, truncated, suppressed, thumbnails skipped/evicted) ship in the "Copy diagnostics" bundle.

**Consumer integration:**

- **Feeds the existing observation tools** — `editor_events` (today a byte-offset NDJSON tail over `Saved/PyMCP/events.ndjson` in `internal/events`) gains a **cockpit-backed live source**: on the native backend it reads the pushed stream (+ durable history from `journal.ndjson`); on the fallback it keeps the byte-offset tail unchanged. Additive migration, no in-place path move.
- **Preserves ordering with results** — `rpc_result`, `progress`, and `event` share one `seq` space on one socket, so an event's order relative to a command result is **exact** (fixes ground-truth §5 split-brain).

Crash *analysis* stays Go-side (`internal/crash` reading `Saved/Crashes/*`) — the in-editor emitter cannot observe its own hard crash.

## 7. Robustness & polish (the "shippable, not a dev hack" bar)

- **Game-thread affinity is the law.** Slate, `UToolMenus`, `GEditor`, `USelection`, subsystems, and all `FEditorDelegates` are game-thread only. **All socket I/O is off-thread** (`FTcpListener` accept + `FRunnable` rx). Every op that touches the editor marshals onto the game thread; event drain and **chunked Tier-N** work honor a hard **≤2 ms/tick** cap on `FTSTicker::GetCoreTicker()`. **Honest exception (§2.6):** a monolithic Tier-P op is a single indivisible game-thread item that can and will exceed the budget; the watchdog surfaces it as `editor.busy`, and the *in-editor* Slate strip is unresponsive for its duration — which is why the **primary human surface is out-of-process** and stays live. We claim to (a) never hitch from *our own* overhead, (b) keep long work off the game thread, (c) **yield the thread back to the human between ops (§4.4)**, and (d) make any op-body hitch visible on a surface the freeze does not touch.
- **Idle *and* BUSY budgets, both gated, both numeric.** Idle: in-editor strip < **0.3 ms/frame**. **BUSY (the dangerous case): a synthetic log-storm + property-storm load test is a Phase-A gate** — the ring stays bounded (drop-oldest fires, `dropped` markers emit, replay recovers), **producers' worst-case enqueue latency under N contending threads stays within budget** (per-thread staging, §6.2), the drain holds ≤2 ms/tick, and the **Go-hosted surface stays live and acks STOP in-browser < 100 ms** (off-thread sever < 50 ms) while a Tier-P op holds the game thread.
- **Co-working budget (fix #2).** With the pacing governor on and a human actively interacting, the editor stays responsive: a Phase-C gate asserts the human's own drag/select cadence holds while an agent op stream runs, i.e. the governor actually returns game-thread cycles (max agent ops/sec honored).
- **Sustained-load budget (fix #11).** An **8-hour SOAK** (Phase D, §8.1) asserts no unbounded growth in memory/handles across the ring, journal rotation, frame retention, `fetch()`-stream reconnect churn, and the virtualized feed.
- **Multi-editor from day one.** The listener binds `127.0.0.1:0` (ephemeral), so N concurrent editors never collide; the assigned port is discovered via `cockpit_info` (§2.4/§2.5), mirroring `spawner.go:74`. The Go daemon hosts **one** cockpit fronting N editors, one pane keyed by project + `session_epoch`, with per-editor STOP + STOP ALL (§3.2).
- **Editor-vs-PIE lifetime.** Never cache `UWorld*` across PIE boundaries; resolve per use and rebind on `BeginPIE`/`PostPIEStarted` / tear down on `EndPIE`. Editor world via `GEditor->GetEditorWorldContext().World()`; PIE worlds are distinct `FWorldContext`s. Delegates are the truth.
- **Reconnect, epochs, and Live Coding.** Forward-connect means Go owns retry. The **plugin-minted `session_epoch`** (not `Generation()`) in `welcome` is the sole authority for "in-editor state reset → replay-from(seq)"; `Generation()` is only a "re-run `cockpit_info`" nudge (§2.5). The transport singleton is **excluded from Live Coding reload** (§2.7), so routine hot-reload does not sever the session; a genuine `MCPCore` reload bumps the epoch → `EDITOR_RESET` → transparent re-attach (§2.5 self-decapitation branch). No tainted-socket churn: framed responses are unambiguous, so a slow op is *progress* (or `editor.busy`), not a closed socket.
- **Cooked-strip.** Cockpit plugin side + native editor ops live in `Editor`/`EditorNoCommandlet` modules — stripped from cooked/shipping. `MCPCapture` stays `Runtime`.
- **Security — bootstrapped over the owned channel (§2.5), and the cockpit UI is authenticated (§3.2), not merely loopback.** Editor channel: loopback-only bind; a **project-scoped, per-session token** returned by `cockpit_info` and echoed in `hello`; the listener refuses non-loopback peers, mismatched tokens, and mismatched projects (parity with `StrictNode`). Cockpit UI: the **same token required on every route** (carried by the `fetch()` bearer header on the event stream, §3.2) + an **Origin/Host allowlist** that defeats CSRF and DNS-rebinding — an unauthenticated local control surface that can Approve destructive ops, STOP, and Force-kill the editor is treated as not shippable. `exec`-class and `scc`-class ops gated by default; `AllowRawExec` hard-mode denies raw exec outright (§5.5); `AgentMaySave`/`AgentMayCheckout` govern SCC/disk writes (§5.2). **No** dependency on Epic's pong for discovery or auth.
- **Settings (`UMCPSettings : UDeveloperSettings`).** A real Project Settings page: listener port **hint (`0`=ephemeral)** + autostart; default approval policy; `GateTimeout` (**clamped to a fraction of the call timeout, §4.2**); **`AllowRawExec`**, **`AgentMaySave`/`AgentMayCheckout`** (§5.2); event-category toggles; **property-observation scope + per-tick cap + bulk-suppression**; undo-batch policy + **`UndoBatchMaxOps`/`UndoBatchMaxMs`** + **redo-deferral window (§4.3)**; **`AgentMayChangeSelection`** + follow-agent (§3.5); **yield-to-human governor: `HumanActiveWindowMs` + `MaxAgentOpsPerSecWhileHumanActive` (§4.4)**; **`RpcQueueDepth` (§5.6)**; **capture caps: `ThumbnailMaxPerSec` / `ThumbnailFrameBudgetMs` / `FrameRetentionCount` / `FrameRetentionBytes` (§6.2)**; **`ForceKillOfferSeconds`**; soft-lock + `ASSET_OPEN_IN_EDITOR` policy (§4.4); log verbosity; ring size; **journal retention/rotation (§4.6)**; redaction rules.
- **UX polish.** First-run toast ("MCP cockpit ready — no agent connected"); color-blind-safe status colors; empty/disconnected states; the in-editor strip's "Open cockpit" launcher and a one-command launch for the Go cockpit; a "Copy diagnostics" button (manifest + last N journal lines + backpressure/property/capture counters + engine/plugin versions); expanded `plugin/UnrealMCP/README.md` covering install/enable/connect, **where the primary vs secondary surface lives and why the Slate strip goes dark mid-op (§2.6/§3.1)**, the cockpit's auth model, the policy model (approval, SCC, raw-exec, pacing), and troubleshooting.

| **Stuck injected input invisible.** | **Live held-key set** (`input.held`) + **`input.released` confirmation** in the PIE/State pane (§3.4/§6.1, fix #12). |
| **Unbounded growth over an all-day session.** | Capture rate/cost/retention caps + journal rotation (§6.2/§4.6); **8 h SOAK gate** (Phase D, fix #11). |
| **Live Coding self-decapitation.** | Transport in a **process-lifetime singleton excluded from Live Coding reload** (§2.7); compile/build via the Go async path; reconnect branch → `EDITOR_RESET` + transparent re-attach (§2.5). |
| **Agent steals the human's selection** (and whips the property window). | **Selection-stewardship contract**: save/restore around non-selecting ops; property scope anchored to the **human's** selection; `AgentMayChangeSelection` (§4.4). |
| **Overclaiming control** (mid-op preemption) / placeholder latency. | §2.6 states the game-thread limit up front; STOP categorized with **numeric budgets**; **honest deferred-STOP = remaining op time, p50/p99 published**; Force-kill after T=10 s; hard-kill is Go-side `lifecycle.Kill` (§4.5). |

### 8.3 Testability

- **Go side:** extend `internal/fakeeditor` (today a double for the uexec reverse-connect protocol) to *also* serve the framed cockpit protocol — handshake, `cockpit_info`/`not_present` sentinel/token, **plugin-minted epoch + the reconnect state machine incl. self-decapitation**, event push, rpc, **bounded queue + `QUEUE_FULL` + exactly-one serialization (§5.6)**, **completion reconciliation → `EDITOR_EXEC_FAILED` (§5.1)**, **gate park + before→after diff + args-hash + re-dispatch + ctx-cancel-cancels-gate + `AGENT_SEVERED` (§4.2)**, cancel, drop-oldest+replay — so `internal/cockpit`, the Go cockpit UI, the exclusive selector, and the event-stream tools are unit/integration-tested with **no editor.** Assert the agent contract (a gated op is held open and returns a normal result on approve; no `PENDING_APPROVAL` surfaced). **Cockpit auth test:** an un-tokened `fetch()` stream/POST is `401`; a mismatched-`Origin`/`Host` request is rejected; a control `POST` without the `Authorization` header is refused. **SSE replay test:** a `fetch()`-stream reconnect with `Last-Event-ID` recovers the gap from the same replay path. **GateTimeout clamp test:** the effective park timeout is provably below the call timeout.
- **C++ side:** factor dispatch/policy/queue/manifest/ring out of Slate (they live in `MCPCore`) → `FAutomationTestBase` specs: classification + **fail-closed default**, **agent-batch grouping + time/size-box + force-close-before-human-undo + no double-wrap + redo-deferral (`CanRedo` gate)**, attribution flag, cancel of chunked Tier-N ops, epoch/replay + **Live-Coding-exclusion survival**, drop-oldest accounting, **per-thread-staging enqueue under N threads**, coalescing, property scope/cap/suppression, **selection save/restore + gate focus/restore**, **`FindEditorsForAsset` → `ASSET_OPEN_IN_EDITOR`**, **package/SCC state → panel events**, **held-input `input.held`/`input.released`**, **per-op thumbnail bounds-framing + cost-budget skip**, **yield-to-human governor rate under simulated human activity**.
- **Conformance (the security gate):** the **bijection test** — every `_OPS` key has a classification and vice-versa — runs on **both** Go and C++, wired into the B2 gate (§5.3).
- **Protocol conformance:** the golden-frame corpus is asserted by both Go and C++ suites.
- **Parity harness:** B1 runs every **structured** op on both backends and diffs results — an empty diff is the gate; `CallText` parity is its own harness.
- **BUSY load test:** a synthetic **log-storm + property-storm** exercises the ring/backpressure/enqueue-latency and asserts the **Go surface stays live + STOP acks < 100 ms** while the game thread is held — an A-phase gate.
- **SOAK test:** the **8-hour sustained run** (fix #11) asserts bounded memory/handles across ring, journal rotation, frame retention, reconnect churn — a Phase-D gate.
- **Live gate:** each phase requires a real two-editor session (matching the multi-project daemon's "live two-editor validation" and the agent-gate culture) before it counts as done.
